# Spec: 子代理模型调用失败在活动面板中的呈现（model call failure activity entry）

Status: ready-for-agent

## Problem Statement

父会话用户派发子代理后，只能通过子代理活动面板观察它在做什么。当子代理调用模型失败时（鉴权失败、配额或限流、请求报错、上下文超限、网络中断……），面板里**什么都没有**：没有条目、没有标记、没有一行文字，用户看到的只是子代理突然静止。

根因不在渲染：面板早已具备完整的红色错误呈现能力（工具失败的行尾标记与可展开的红色原文），但活动条目的正文闭集只有「文本」与「思考」两类块，而失败回合的收尾消息正文为空，在桥接层就被整条丢弃；收尾原因与错误文本从未被复制。于是错误事实在链路最上游消失，后续每一层都没有位置承载它。用户既不知道子代理为什么停下，也无法判断该去查模型配置、查配额还是查网络。

## Solution

新增第四种活动条目种类——**模型调用失败条目**，在桥接层采集失败回合的收尾原因与错误文本，随既有的规范活动契约上行到父端活动缓存，并在子代理活动面板的详情条目流中呈现：折叠态显示一行红色 `× Error: <错误文本首行>`，展开后显示错误原文，身份可得时在其上方显示一行 `provider · model`。

按前置设计会话的结论：**每次失败尝试各出一条**，逐条登记、不撤回、不合并——因此被重试救回的尝试也会留痕；该事实属于活动事实，**不驱动子代理生命周期状态**，也不进入实时显示草稿或父模型上下文。

采集面覆盖两类事实：失败回合的收尾 assistant 消息，以及压缩自身（summarization 调用）失败。压缩自身失败不携带发起它的模型身份，因此条目的 `provider` / `model` 允许缺失——缺失时只是不显示身份行，条目其余部分与呈现完全相同。

## User Stories

1. 作为父会话用户，我想在子代理调用模型失败后于活动面板看到一条明确的失败记录，以便知道它为什么停下来，而不是只看到它突然静止。
2. 作为父会话用户，我想一眼分辨这条失败是"模型调用失败"而不是"工具执行失败"，以便判断该去查模型配置还是查工具。
3. 作为父会话用户，我想在折叠态看到一行简短摘要，以便不展开就能扫过整段历史。
4. 作为父会话用户，我想展开失败条目查看完整错误原文，以便拿到 provider 返回的原始报文去查证。
5. 作为父会话用户，我想在展开的正文里看到发起失败的 provider 与模型，以便在子代理配置了多个模型时判断是哪一个出了问题。
6. 作为父会话用户，我想多行错误保留其换行结构，以便原始 JSON 或登录引导文案不被压成一行难以阅读。
7. 作为父会话用户，我想过长的错误行按面板既有规则截断或折行，以便面板布局不被超长行破坏。
8. 作为父会话用户，我想在子代理因上下文超限失败时看到失败条目，以便决定压缩上下文还是换模型。
9. 作为父会话用户，我想在子代理被中断后看到一条"已中止"记录，以便区分"我打断了它"和"它自己出错了"。
10. 作为父会话用户，我想失败条目在图标与颜色上与普通消息、工具条目有区分，以便快速定位。
11. 作为父会话用户，我想失败条目不改变子代理的生命周期状态显示，以便"停止工作"与"出错"不被混淆。
12. 作为父会话用户，我想错误文本缺失时看到兜底文案，以便至少知道这次调用失败了。
13. 作为父会话用户，我想在"模型先输出半句再失败"时同时看到已生成的正文与失败记录，以便不丢失已有内容。
14. 作为父会话用户，我想同一回合的多次失败尝试各自成条，以便看到真实发生了多少次失败。
15. 作为父会话用户，我想"重试后最终成功"的回合里此前的失败尝试仍留痕，以便理解子代理曾经抖动过。
16. 作为父会话用户，我想失败条目按发生顺序出现在历史时间线中，以便回溯过程。
17. 作为父会话用户，我想失败条目遵守面板既有的滚动、选中与展开交互，以便操作方式不因新条目改变。
18. 作为父会话用户，我想失败条目在活动窗口裁剪时与其它条目同等待遇，以便行为可预期。
19. 作为父会话用户，我想面板宽度变化时失败条目按新宽度重新折行，以便自适应不同终端宽度。
20. 作为父会话用户，我想反复失败时错误条目照旧各自成条、不被合并或节流，以便不丢失失败次数这一事实。
21. 作为父代理，我想子代理的模型失败不进入我的模型上下文，以便观测信息不消耗我的上下文预算。
22. 作为父代理，我想在子代理模型失败后仍能用既有控制手段继续处理它，以便失败不改变我对它的控制能力。
23. 作为扩展维护者，我想新增条目种类在产生端、接收端、活动缓存与查看器四处同时就位，以便版本一致时不会有条目被拒。
24. 作为扩展维护者，我想规范活动契约版本与监督协议版本同步递增，以便不同版本不会被误当成兼容。
25. 作为扩展维护者，我想"版本一致时活动链路故障不得把子代理判为失败"成为可测试的验收项，以便面板永远不会拖垮子代理。
26. 作为扩展维护者，我想新增条目遵守既有的安全闭集、身份约束与帧预算约束，以便不引入越界数据或超预算帧。
27. 作为扩展维护者，我想查看器对无法识别的条目保持既有忽略行为，以便将来扩展种类时不会崩坏面板。
28. 作为子代理，我想我的模型失败被如实记录却不影响我的运行，以便观测能力不成为新的失败源。
29. 作为子代理，我想错误文本只在版本一致的父子之间流动，以便不同版本不互相污染活动历史。
30. 作为实现者，我想测试能在不依赖真实模型的前提下复现"失败消息 → 面板显示"，以便用例稳定可重复。
31. 作为实现者，我想"采集自动重试事件"这类扩展被明确排除，以便桥接事件闭集不被动摇。
32. 作为父会话用户，我想在子代理压缩自身失败（拿不到发起失败的模型身份）时也看到失败条目，以便不让这类失败悄悄消失。
33. 作为父会话用户，我想在拿不到 provider/model 时展开体不显示身份行，以便不看到占位符或空行。
34. 作为扩展维护者，我想压缩失败的采集只新增产生端订阅、不动桥接/RPC 事件闭集，以便观测能力不扩大跨端协议面。

## Implementation Decisions

### 数据面

- **新增第四种活动条目种类「模型调用失败条目」**（与消息、父消息、工具并列），承载一次模型调用失败事实。决策形状（由前置设计会话确定）：

```
model_call_failure body:
  kind: "model_call_failure"
  failure: "error" | "aborted"   // 收尾原因，如实采集
  message: string                // 错误文本；缺失时为 "Unknown error"
  provider?: string              // 压缩自身失败等场景不可得时整个字段缺失
  model?: string
```

- **保留收尾原因但不参与呈现分支**：`failure` 如实记录"错误"与"已中止"，当前两种呈现完全相同（同一图标、同一文案前缀）；保留它是为了不丢失事实本身，将来若要区分无需再动契约。
- **兜底文案**：错误文本缺失（理论上存在——provider 只给状态不给正文）时使用 Pi 自身 TUI 的兜底字符串 `Unknown error`，不自造新文案。
- **身份字段可为空且同进同出**：`provider` 与 `model` 要么同时在场、要么同时缺失；缺失时条目仍完整成立（`failure` 与 `message` 始终在场），呈现层只是省略身份行，不写占位文案、不留空行。
- **不携带**用量、原生收尾原因、诊断数组等其它字段：它们是 Pi 消息上的调试信息，不属于本次要表达的"模型调用失败"。

### 采集面

- **采集点一（收尾 assistant 消息）**：失败事实就在收尾 assistant 消息上（收尾原因 + 错误文本），桥接层在把 Pi 原始事件归一化为安全活动事件时一并读取；该路径不新增 Pi 事件订阅点。
- **采集点二（压缩自身失败）**：`session_compact_failed` 携带 `errorMessage` 与 `aborted`，子代理运行时扩展新增该产生端订阅，沿既有产生端归一化路径登记为模型调用失败条目（`aborted` 为真记 `aborted`，否则记 `error`；文本缺失时用兜底文案），身份字段缺失。该订阅只发生在产生端扩展，**桥接/RPC 事件闭集保持不变**。
- **上下文超限走压缩失败通道**：带错误文本的压缩失败同样采集为模型调用失败条目；**没有错误文本的静默溢出**（只体现为用量超窗口或长度收尾且零输出）不采集、不自造文案。超限失败（采集点一，带身份）与随后可能发生的压缩自身失败（采集点二，无身份）是两个独立事实，各自成条、不合并、不去重。
- **不采集重试事件**：桥接事件闭集保持不变，不引入 `auto_retry_start` / `auto_retry_end`，也不采集压缩重试事件 `summarization_retry_scheduled` / `summarization_retry_attempt_start` / `summarization_retry_finished`，因此条目上不显示"第几次尝试"。
- **每条尝试独立成条**：每次失败尝试产生一条独立条目，拥有自己的条目身份；不判定"最终失败"，不做延迟发布，不撤回已登记的条目。
- **正文为空的失败消息不再被整条丢弃**：归一化规则从"正文为空即忽略"改为"正文为空但携带失败事实时登记为模型调用失败条目"；正文非空的失败消息同时产生一条消息条目与一条失败条目（两条独立）。
- **错误文本原样**：不做翻译、不做摘要、不做分类、不加自己的前缀（呈现前缀是显示层的事）。

### 呈现面

- **位置**：仅出现在活动面板的详情条目流中；不在 agent 行或面板标题上添加标记。
- **折叠态**：`▸ × Error: <错误文本首行>`；超宽按面板既有截断规则处理（右侧省略号），与工具条目一致。
- **展开态**：身份可得时第一行是 `provider · model`，其后是错误文本原文；身份缺失时正文直接以错误文本原文开头，不留空行、不写占位文案。正文逐字、保留换行、保留前导空白、按宽度软折行，使用面板既有的红色预格式化正文渲染（与工具失败展开体同款）。
- **不显示时间戳**；**不新造"还有 N 行"折叠提示**（面板既有折叠提示只有展开标记，与工具条目一致）。
- **样式**：图标 `×`、行样式为错误色，与工具失败条目一致；`已中止` 与 `错误` 使用完全相同的呈现。
- **交互**：沿用面板已有的展开/折叠与选中机制，不新增任何操作入口（不做重试、复制、跳转）。

### 语义与边界

- **活动事实，不是生命周期事实**：模型调用失败条目**不**把子代理判为失败、不触发任何生命周期状态转换、不改变控制屏障。
- **不进入实时显示草稿**：草稿仍只服务文本与思考的实时预览；失败条目只进入活动条目历史，与既有条目同等待遇（含活动窗口的裁剪规则），也不进入条目计数之外的任何父模型上下文。
- **与工具失败严格分开**：不复用工具失败的错误码/正文语义，也不把工具失败改写为模型调用失败。
- **不合并、不节流、不去重**：同一回合的多次失败、跨回合的重复失败，一律各自成条。

### 契约与兼容

- **规范活动契约版本递增一位**，监督协议版本同步递增；两个常量一起改，避免出现"监督协议一致但活动契约不一致"的错配窗口。
- **本次扩展并入尚未发布的契约版本**：v0.5.1 发布的是 `activity/11` 与协议 `/29`；当前已升至 `activity/12` 与 `/30` 但尚未发布，字段可空与压缩采集一并并入该版本，不再升版。若该版本已对外发布，则两个常量各自再递增一位，且同样不提供兼容层。
- **版本不一致按既有兼容性边界处理**：不认领、不转换、不迁移旧会话，不做兼容层，不降级为消息发送失败。
- **版本一致时新条目必须被完整接受**：接收端对模型调用失败条目的闭集校验必须与产生端同时就位，不得被判为无效帧。

### 模块影响

- **桥接事件归一化**：从收尾消息读取收尾原因与错误文本；正文为空的失败消息产生失败条目；此路径不新增订阅点。
- **产生端压缩失败采集**：子代理运行时扩展订阅 `session_compact_failed`，把错误文本与中止标志归一化为无身份的失败条目，沿既有产生端活动路径登记。
- **规范活动契约**：新增条目正文种类、闭集校验、契约版本常量。
- **活动缓存**：接受新条目种类并纳入既有窗口/墓碑/序号机制。
- **活动查看器**：新增条目种类的渲染与展开体（复用既有错误样式与预格式化正文布局）。
- **控制器活动转发与监督通道**：新条目沿既有活动帧路径上行/分发；帧闭集与身份校验同步覆盖。

## Testing Decisions

- **好测试的标准**：只断言外部可观察行为——面板渲染出的文本行、活动缓存快照里的条目序列、帧级"被接受/被拒绝"的结果；不断言内部字段结构、私有状态或调用次数。用例名写成中文行为陈述句（本仓库既定风格）。
- **主接缝（唯一新增用例接缝）**：进程内全链装配——桥接事件归一化 → 监督通道帧 → 树控制器/控制器活动缓存 → 活动源 → 面板渲染。这是能同时覆盖"错误文本被采集"和"面板真的显示出来"的最高接缝，不需要新造任何桩。
- **复用既有接缝（不新增接缝）**：
  - 规范活动契约测试套件：契约版本断言随递增更新、新条目形状的闭集校验与拒绝。
  - 监督通道测试套件：新条目在版本一致时跨端发布/接收必须被接受。
  - 控制器活动测试套件：活动链路转发异常被吞掉、不沿事件回调传播（既有同方向用例已存在，新增用例补充"不导致子代理失败"的断言）。
  - 真实桥接进程测试套件：以脚本化伪 Pi 播放"正文为空且带错误文本"的收尾消息，回归跑通。
  - 扩展运行时测试套件：以脚本化扩展事件驱动产生端订阅，断言压缩自身失败的登记与压缩重试事件的忽略。
- **必须覆盖的验收用例**：
  1. 版本一致时，收尾原因为错误且正文为空的收尾消息在面板上产生一条 `× Error:` 条目。
  2. 已中止的收尾在面板上产生同形条目。
  3. 错误文本缺失时条目显示兜底文案。
  4. 展开体包含 provider 与模型，以及逐字保留换行的错误原文。
  5. 正文非空的失败消息产生两条独立条目（正文条目 + 失败条目）。
  6. 上下文超限的压缩失败在有错误文本时产生条目；无错误文本的静默溢出不产生条目。
  7. 自动重试相关事件仍被忽略，不产生任何条目。
  8. 同一回合的多次失败各自成条，顺序即到达顺序。
  9. 失败条目不改变该子代理的生命周期状态（与既有"活动事实不影响生命周期"用例同方向）。
  10. 失败条目不进入实时显示草稿投影。
  11. 契约版本递增后，旧版本条目仍按不兼容处理（发布端拒绝、接收端按协议故障）。
  12. **版本一致时，活动链路故障不得把子代理判为失败**（硬约束的验收项）。
  13. 压缩自身失败（`session_compact_failed` 带错误文本）产生一条条目，且该条目不携带 provider/model。
  14. 压缩自身失败被中止（`aborted` 为真）时产生同形条目。
  15. 身份缺失的条目展开体不出现身份行、正文以错误原文开头；身份存在时展开体行为不变。
  16. 压缩重试事件（`summarization_retry_*`）与自动重试事件一样不产生任何条目。
- **不自动化**：真实模型端到端验证（真的打到失败配额/错误密钥）作为手工验收步骤，不进入 `npm test`。

## Out of Scope

- **把活动/显示层故障改成不影响通道**：现状是"无法解析的活动帧会把整条监督通道置为故障"，本次只保证版本一致时不会出现无法解析的条目，不反转该协议裁决；如需改造另开 effort。
- 采集 `auto_retry_*` 或显示"第几次尝试/共几次"。
- 压缩重试事件 `summarization_retry_scheduled` / `summarization_retry_attempt_start` / `summarization_retry_finished`（与 `auto_retry_*` 同属重试类，产生端与桥接都不采集）。
- 无错误文本的静默上下文溢出。
- 错误的分类、翻译、摘要生成或智能归因。
- 条目的合并、节流、去重与"同类错误折叠"。
- 任何操作入口（重试、复制原文、跳转）。
- 把最近一次模型错误暴露给父代理的编程接口（`wait_agent` / 状态查询返回里带上）。
- agent 行或面板标题上的失败标记。
- 启动期模型不可用/未知 provider 的诊断（既有启动诊断已覆盖）。
- 生命周期语义调整（模型失败不进入 `failed`）。
- 历史条目的回填或迁移（旧版本条目不被转换）。

## Further Notes

- **调研依据**：Pi 把模型调用失败编码在收尾 assistant 消息的收尾原因与错误文本上，而不是独立事件；压缩自身失败是例外——它只在 `session_compact_failed`（扩展事件）与 `compaction_end`（RPC 事件）上暴露，两者都不携带 provider/model；出错时回合照常收束，收束事实本身不带任何错误信息；进程内扩展看不到尝试级的重试事件，因此本次刻意不依赖它。错误文本形态包括 provider 原始报文、Pi 直译的收尾短语与 Pi 自行合成的引导文案，可能多行、可能含原始 JSON。
- **术语**：`CONTEXT.md` 已收录"模型调用失败"与"模型调用失败条目"两条术语，并把"运行故障""失败状态"等词列为应避免的用法——模型调用失败是活动事实，不是生命周期状态。
- **决策记录**：取舍（为什么独立条目、为什么不挂到消息上、为什么不延迟判定最终失败、为什么扩契约两次不划算）见 `docs/adr/0001-model-call-failure-activity-entry.md`。
- **明确接受的副作用**：父代理每次中断子代理都会在面板留下一条"已中止"条目；重试耗尽时会出现多条几乎相同的红色条目。
- **明确接受的副作用（补充）**：压缩自身失败会留下一条没有身份行的条目；同一次事件链上若先有超限失败，面板会相邻出现两条（前者带身份、后者不带）。
- **复用既有能力**：红色错误样式、可展开的预格式化正文、行截断与软折行、面板滚动/选中/展开交互全部沿用，不为本特性新造渲染机制。
- **已知隐患（本次不改）**：活动帧校验失败会连带通道故障；因此验收用例 12 专门钉住"版本一致时活动链路故障不得导致子代理失败"。
